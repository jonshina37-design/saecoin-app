1. PURPOSE

This document defines the referral system requirements for the SAECOIN App.

The referral system allows existing users to invite new users through unique referral codes or links.

A referred account may qualify for referral-related Mining Power bonuses after completing the required mining activity.

The system must be secure, transparent, auditable, and controlled by the backend.

This document covers:

- Referral code generation.
- Referral registration and acceptance.
- Referral limits.
- Qualification requirements.
- Referral Mining Power bonuses.
- Active mining eligibility.
- Referral reward budget.
- Fraud prevention.
- Referral history.
- Backend APIs.
- Database relationships.
- Administrative controls.
- Testing requirements.

2. SCOPE AND IMPORTANT DISTINCTION

The referral system belongs exclusively to the SAECOIN App Mining reward system.

It does not represent blockchain mining.

Referral bonuses are virtual App Mining reward calculations.

They do not create on-chain SAC, cryptocurrency transactions, or guaranteed monetary value.

Future blockchain mining will be handled separately.

3. REFERRAL ROLES

The system has two participants.

3.1 Referrer

The existing user who shares a referral code or link.

Responsibilities:

- Maintain an eligible account.
- Share their referral code.
- Follow referral program rules.
- Avoid fraudulent or misleading referral activity.

3.2 Referred User

The new user who registers using a valid referral code or link.

Responsibilities:

- Register through the normal registration process.
- Complete required account verification.
- Complete 21 successful mining sessions.
- Follow account and mining rules.

4. REFERRAL CODE SYSTEM

Every eligible user should receive a unique referral code.

The referral code must:

- Be generated by the backend.
- Be unique across the system.
- Be associated with one user.
- Be difficult to guess.
- Be validated by the backend.
- Not expose internal user IDs.
- Not be freely editable by users.

A shareable referral link may contain the referral code.

4.1 Code Format

The final code format and length are TBD.

The format should support:

- Easy copying.
- Easy sharing.
- Case-insensitive or consistently normalized validation.
- Collision prevention.

4.2 Code Security

The backend must:

- Prevent duplicate codes.
- Reject invalid codes.
- Prevent unauthorized code ownership changes.
- Apply reasonable rate limits to code validation.
- Avoid revealing unnecessary account information during code lookup.

5. REFERRAL REGISTRATION FLOW

The proposed registration flow:

1. Existing user opens the Referral screen.
2. App displays the user's referral code and sharing link.
3. Existing user shares the link or code.
4. New user opens the link or enters the code.
5. Backend validates the code.
6. New user completes registration.
7. Backend creates the referral relationship.
8. Referral receives the appropriate initial status.
9. New user begins App Mining activity.
10. Backend tracks successful mining sessions.
11. After 21 successful sessions, qualification is evaluated.
12. Eligible referral bonuses may be calculated when the relevant participants are actively mining.

The backend must be authoritative throughout this process.

6. REFERRAL ACCEPTANCE RULES

The following rules apply:

1. A referral must be attached through an approved registration process.
2. A user cannot refer themselves.
3. A user cannot have multiple referrers.
4. A referral relationship must not be duplicated.
5. A referrer may have a maximum of 10 accepted referrals.
6. Invalid or expired referral codes must be rejected.
7. Referral ownership must be recorded by the backend.
8. Referral relationships must be auditable.

Whether a referral can be changed after acceptance is a pending policy decision.

The implementation must not allow users to change referral ownership without an approved backend rule.

7. MAXIMUM REFERRAL LIMIT

Each referrer may have a maximum of:

10 accepted referrals.

The backend must enforce this limit.

Important requirements:

- Pending registration attempts must not be treated as accepted referrals.
- The exact point at which a referral becomes accepted must be defined by the registration workflow.
- Concurrent registration requests must not allow the limit to be exceeded.
- Rejected, expired, or revoked referrals must be handled according to an approved counting policy.

The counting policy for revoked referrals is TBD.

8. REFERRAL QUALIFICATION

A referred user becomes qualified after completing:

21 successful mining sessions.

A successful session must satisfy the Mining Reward Specification.

A session is not successful merely because the user starts mining.

The backend must verify:

- Session start.
- Required eight-hour duration.
- Session completion.
- Daily session limits.
- Account eligibility.
- Duplicate request prevention.
- Any required session validation.

Only backend-confirmed successful sessions count toward referral qualification.

9. REFERRAL STATUS

Each referral must have a clearly defined status.

Proposed statuses:

Status| Description
PENDING| Referral registration has started but acceptance is not complete.
ACCEPTED| Referral relationship has been successfully created.
QUALIFIED| Referred user has completed 21 successful mining sessions.
REVOKED| Referral relationship has been invalidated through an authorized process.
EXPIRED| Referral has expired under an approved expiry policy.

9.1 Valid State Transitions

Proposed transitions:

- PENDING → ACCEPTED
- PENDING → REVOKED
- PENDING → EXPIRED
- ACCEPTED → QUALIFIED
- ACCEPTED → REVOKED
- ACCEPTED → EXPIRED
- QUALIFIED → REVOKED

A referral must not move backward from QUALIFIED to ACCEPTED.

A revoked or expired referral must not become qualified automatically.

Any exceptional correction must be performed through an authorized administrative process and recorded in the audit log.

9.2 Qualification Verification

The backend must calculate qualification using successful session records.

The frontend must not be able to directly change referral status.

10. REFERRAL MINING POWER BONUS

The referral system uses Mining Power bonuses.

It does not automatically award a fixed amount of SAC for every referral.

After a referred user becomes qualified:

- The referrer may become eligible for a referral Mining Power bonus.
- The referred user may also become eligible for a referral Mining Power bonus.

Each participant's eligibility is evaluated independently.

10.1 Active Mining Requirement

A participant receives the referral Mining Power bonus only when that participant is actively mining in the relevant session.

The following rules are mandatory:

1. Referrer is actively mining: referrer may receive the bonus.
2. Referred user is actively mining: referred user may receive the bonus.
3. Referrer is inactive: referrer receives no bonus for that session.
4. Referred user is inactive: referred user receives no bonus for that session.
5. One participant's inactivity must not prevent the other active participant from receiving an eligible bonus.

10.2 No Deferred Bonus

An inactive participant's missed referral bonus:

- Must not be stored for later.
- Must not be accumulated.
- Must not be transferred to another session.
- Must not be paid automatically when the participant becomes active again.

Eligibility must be evaluated separately for every relevant mining session.

10.3 Independent Eligibility Examples

Referrer| Referred User| Result
Active| Active| Both may qualify.
Active| Inactive| Only referrer may qualify.
Inactive| Active| Only referred user may qualify.
Inactive| Inactive| Neither receives a bonus.

These rules apply only after the referral relationship has qualified and remains valid.

11. REFERRAL BONUS FORMULA

The exact referral bonus percentage and calculation method are TBD.

A 5% bonus was discussed as a possible proposal, but it has not been approved.

The final formula must be documented in the Mining Reward Specification before implementation.

The formula must define:

- Bonus percentage.
- Eligible Mining Power.
- Calculation timing.
- Rounding rules.
- Daily referral budget interaction.
- Behavior when the referral budget is exhausted.

No developer may independently introduce a bonus percentage or multiplier.

12. REFERRAL DAILY REWARD BUDGET

The current provisional referral bonus allocation is:

1,000 SAC per day.

This allocation is part of the proposed 6,000 SAC daily App Mining reward budget.

The referral allocation is not additional to the total daily budget.

The backend must enforce:

- Referral rewards do not exceed the approved referral budget.
- Referral rewards do not exceed the total daily reward budget.
- Concurrent processing cannot exceed the budget.
- Duplicate reward processing is prevented.
- All reward calculations are recorded in the reward ledger.

The handling of referral bonuses when the daily budget is exhausted is TBD.

No automatic rollover of unused daily referral budget is permitted unless an approved policy explicitly allows it.

13. REFERRAL REWARD PROCESSING

The proposed processing sequence:

1. Backend confirms the referral is valid.
2. Backend confirms the referred account is qualified.
3. Backend checks the referrer's eligibility.
4. Backend checks the referred user's eligibility.
5. Backend checks whether each participant is actively mining.
6. Backend calculates eligible Mining Power bonuses.
7. Backend checks the remaining referral budget.
8. Backend records approved reward calculations.
9. Backend updates the reward ledger through the approved reward-processing workflow.
10. Backend records processing results.

Referral bonus calculation and reward settlement must be consistent with "08-Mining-Reward-Specification.md".

A referral bonus record must not independently create an SAC balance outside the reward ledger.

14. FRAUD PREVENTION

The referral system must include controls against abuse.

Prohibited behavior includes:

- Self-referral.
- Creating multiple accounts to obtain referral benefits.
- Fake or automated registrations.
- Referral code manipulation.
- Repeated registration attempts.
- Referral relationship manipulation.
- Coordinated fake account activity.
- Attempts to bypass the 10-referral limit.
- Attempts to manipulate mining session records.
- Unauthorized referral changes.

The backend may use risk signals such as:

- Repeated device identifiers.
- Suspicious registration patterns.
- Unusual referral velocity.
- Shared technical identifiers.
- Repeated account relationships.
- Abnormal session completion patterns.

These signals must be used carefully.

A shared device or network alone should not automatically prove fraud.

The system should support review and documented decisions.

15. REFERRAL REVOCATION

A referral may be revoked when:

- Fraud is confirmed.
- The referral was created through unauthorized activity.
- The referred account is found to be invalid.
- The referral relationship was created incorrectly.
- An authorized administrator approves revocation.

Revocation requirements:

1. Record the reason.
2. Record the administrator or system process responsible.
3. Preserve the original referral record.
4. Preserve related reward history.
5. Prevent future referral bonuses from the revoked relationship.
6. Handle previously issued rewards according to the approved reward reversal policy.

Previously recorded reward entries must never be silently deleted.

Any reward adjustment must be recorded as a separate ledger entry.

16. REFERRAL EXPIRATION

Referral expiration rules are TBD.

The final policy must define:

- Whether referral codes expire.
- Whether pending referrals expire.
- Whether accepted but unqualified referrals expire.
- Whether a qualified referral remains valid permanently.
- What happens when an account is inactive or cancelled.

Until approved, the backend must not introduce arbitrary expiration periods.

17. REFERRAL USER INTERFACE

The Referral screen should display:

- User's referral code.
- Copy referral code action.
- Share referral link action.
- Total accepted referrals.
- Maximum referral limit.
- Referral list.
- Referred user's qualification status.
- Referral bonus history.
- Relevant referral rules.

The interface must clearly distinguish:

- Pending referrals.
- Accepted referrals.
- Qualified referrals.
- Revoked or expired referrals.

The app must not display a referral as qualified before backend confirmation.

The app must not promise a fixed SAC amount or guaranteed monetary value.

18. REFERRAL NOTIFICATIONS

The system may send notifications for:

- Successful referral acceptance.
- Referral qualification.
- Referral revocation.
- Referral expiration.
- Referral bonus processing.
- Referral-related account restrictions.

Notifications must reflect confirmed backend events.

The app must not send misleading notifications suggesting that a pending referral has already earned a reward.

19. BACKEND API REQUIREMENTS

Suggested API routes:

Method| Endpoint| Purpose
GET| "/api/v1/referrals/me"| Get current user's referral information.
GET| "/api/v1/referrals/me/list"| Get referral list.
GET| "/api/v1/referrals/me/summary"| Get referral summary.
GET| "/api/v1/referrals/validate/{code}"| Validate a referral code.
POST| "/api/v1/referrals/accept"| Attach a referral during an approved registration flow.
GET| "/api/v1/referrals/me/rewards"| Get referral bonus history.

Administrative endpoints must use separate protected routes and permissions.

The exact API request and response schemas will be finalized in the API implementation.

19.1 Backend Security

The backend must:

- Authenticate protected requests.
- Validate referral ownership.
- Enforce the referral limit transactionally.
- Prevent duplicate relationships.
- Prevent unauthorized referral changes.
- Apply rate limits.
- Record important referral actions.
- Avoid exposing private user information.

20. DATABASE REQUIREMENTS

The referral system must use the database structures defined in:

"07-Database-Schema.md"

Relevant tables include:

- "referrals"
- "referral_bonus_records"
- "users"
- "mining_sessions"
- "reward_ledger"
- "audit_logs"

The database must preserve:

- Referrer user ID.
- Referred user ID.
- Referral code or attribution reference.
- Referral status.
- Acceptance timestamp.
- Qualification timestamp.
- Revocation or expiration information.
- Related reward calculation records.

Exact columns, indexes, constraints, and data types must follow the finalized database implementation.

20.1 Data Integrity

The database must enforce:

- One accepted referrer relationship per referred account.
- Unique referral relationship identifiers.
- Valid user references.
- Prevention of duplicate reward records.
- Appropriate status constraints.
- Consistent reward ledger references.

The 10-referral limit must be enforced safely under concurrent requests.

21. ADMINISTRATIVE CONTROLS

Authorized administrators may need to:

- View referral relationships.
- Review suspicious referrals.
- Investigate abuse reports.
- Revoke invalid referrals.
- Review referral bonus records.
- Review referral-related audit logs.
- Approve authorized corrections.

Administrative actions must:

- Require appropriate permissions.
- Include a reason.
- Be recorded in audit logs.
- Preserve historical records.
- Follow the reward ledger adjustment rules.

Administrators must not directly edit reward balances without an auditable ledger operation.

22. PRIVACY AND USER PROTECTION

The referral system must follow the project's privacy and security requirements.

Rules:

- Do not request social media passwords.
- Do not scrape a user's private contacts.
- Do not upload contact lists without explicit consent and an approved privacy design.
- Do not expose private information about referred users.
- Do not reveal sensitive fraud-detection signals to ordinary users.
- Do not send unsolicited referral messages on behalf of users.
- Allow users to share referral links through normal device sharing features.

26. FINAL POLICY

The SAECOIN referral system must reward genuine user participation rather than account creation alone.

Referral qualification must depend on verified mining activity.

Referral bonuses must follow the approved Mining Power and reward-budget rules.

The system must prevent self-referral, duplicate relationships, reward manipulation, and unauthorized changes.

All referral activity and reward calculations must remain auditable.

Referral bonuses must never be represented as guaranteed cash, guaranteed market value, or already-issued on-chain SAC.
